## Content

### Description
Add schema-validated environment variable loading and runtime fail-fast behavior so missing or malformed config crashes the app with a clear, secret-safe error before serving any traffic.

### Business Context
Config mistakes are one of the most common production outages. Without a typed env loader, secrets leak into logs, services start with wrong defaults, and "why doesn't it work?" eats engineering time. This needs to be in place before Sprint 2 starts adding real config (auth secrets, DB connection strings, JWT keys).

### Problem Statement
Both `apps/api` and `apps/web` currently read `process.env.*` directly. Direct env access is fragile, untyped, and risks logging raw values during debugging.

### Scope
- `packages/config`:
  - `env.schema.ts` defining a zod schema with required and optional fields:
    - `NODE_ENV` (enum: development | test | staging | production).
    - `API_PORT` (default 3001).
    - `WEB_PORT` (default 3000).
    - `DATABASE_URL` (required URL).
    - `REDIS_URL` (required URL).
    - `LOG_LEVEL` (enum: trace | debug | info | warn | error; default info).
    - `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` (placeholder; required in Sprint 2 but stub here).
  - `loadConfig()` that:
    - Parses `process.env` against the schema.
    - On failure: logs only the offending key names and a one-line reason, then exits with code 1.
    - On success: returns a frozen typed config object.
  - `index.ts` re-exporting `loadConfig` and the inferred `AppConfig` type.
- `apps/api/src/main.ts` calls `loadConfig()` before bootstrap; aborts if it throws.
- `apps/web` consumes only `NEXT_PUBLIC_*` subset via a separate validated schema (`web-env.schema.ts`).
- `.env.example` at repo root listing every variable with a comment per variable.
- `.gitignore` covers `.env`, `.env.local`, `.env.*.local`.
- Rule (lint or code review): no direct `process.env.X` outside `packages/config`. Enforced via ESLint custom rule or a project convention documented in CODEOWNERS.

### Technical Notes
- zod is the validator (already used in PF-006 for event contracts; reuse).
- Do not call `loadConfig()` more than once per process.
- The frozen config object prevents accidental mutation at runtime.

### Security Considerations
- Validation errors NEVER print raw values — only key names and reason.
- `JWT_ACCESS_SECRET` and similar fields must NOT appear in error messages even when missing (use `redact: true` flag).
- Avoid logging the full `loadConfig` result; log a sanitized summary with secrets replaced by `***`.

### Performance Considerations
- `loadConfig()` runs once at startup; performance is not a concern.

### Edge Cases
- `NODE_ENV=test` may relax some required fields (e.g. JWT secrets get test defaults).
- Boolean env vars must accept `"true"`, `"false"`, `"1"`, `"0"` (zod coercion).
- Numeric env vars must coerce from strings.
- Missing `.env` file in dev should fall back to `process.env` only (do not crash dev tooling).

## Delivery

### Acceptance Criteria
- [ ] `packages/config` exports `loadConfig()` and `AppConfig` type.
- [ ] Starting `apps/api` with `DATABASE_URL` missing fails fast with a clear error naming the missing key. The error does NOT print other env values.
- [ ] Starting `apps/api` with `DATABASE_URL` set to a non-URL string fails fast with a clear validation error.
- [ ] Starting `apps/api` with all required vars present succeeds and the API serves `/healthz`.
- [ ] No file outside `packages/config` references `process.env` (verified by grep in CI step, or by ESLint custom rule).
- [ ] `.env.example` lists every variable with a comment.

### Testing Requirements
- Unit tests in `packages/config` covering: missing required, wrong type, default applied, frozen object behavior.
- Test that `loadConfig({ JWT_ACCESS_SECRET: undefined })` error message does NOT contain the literal key "JWT_ACCESS_SECRET" in its raw redacted form (or alternatively does contain the key name only, never a value).
- CI greps for `process.env` outside `packages/config/` and fails on hits.
