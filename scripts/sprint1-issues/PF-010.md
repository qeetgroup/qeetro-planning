## Content

### Description
Establish the unit, integration, and component test harness plus a tenant-scoped seed/fixture strategy so every later domain has cheap, predictable verification.

### Business Context
Every Sprint 2+ domain (auth, identity, organizations, issues, boards) needs to ship with tests. If we don't establish the harness and fixture factories now, every domain will reinvent test setup and tenant isolation will be tested inconsistently. Tenant-isolation regressions are existential per [§16 risks](../../docs/planning/04-issue-catalog.md).

### Problem Statement
No test infrastructure exists. The first domain test (likely AUTH in Sprint 2) needs the conventions, factories, and fixtures already in place.

### Scope
- `packages/testing`:
  - Vitest base config preset.
  - `createTestContext()` factory that returns a freshly migrated DB schema, a Prisma client bound to it, and tenant-scoped fixture helpers (`makeOrganization`, `makeUser`, `makeMembership`).
  - Tenant scoping enforced by the factory: every fixture must require an `organizationId` (or auto-create one).
  - Cleanup helper that truncates all tables between tests.
- `apps/api`:
  - Vitest setup for unit tests.
  - `nestjs-test` style E2E setup with `@nestjs/testing` and `supertest` against the API.
  - Example unit test (`HealthService`) and example E2E test (`/api/v1/healthz`).
- `apps/web`:
  - Vitest + React Testing Library for component smoke tests.
  - Example component test for the shadcn `Button` re-export from `@qeetro/ui`.
- Seed data:
  - `apps/api/test/seeds/baseline.ts` that creates one org, one user, one membership — explicitly tenant-scoped.
  - `packages/testing/src/factories.ts` exporting reusable factories that all accept `organizationId`.
- Repo-root scripts:
  - `pnpm test` → runs all unit tests across workspaces.
  - `pnpm test:integration` → runs integration tests (requires DB running).
  - `pnpm test:watch` → watch mode.

### Technical Notes
- Use Vitest, not Jest, for speed and ESM-native support.
- Use `pg-mem` or a real Postgres test DB. Prefer real Postgres in CI (service container from PF-009) and locally; reject `pg-mem` because of FTS/extension differences.
- Test DB per test file via Prisma's `$executeRaw("CREATE SCHEMA ...")` pattern, OR a single test DB with `BEGIN/ROLLBACK` per test. Pick one and document.
- React Testing Library v15+.
- `supertest` for API e2e (or NestJS's built-in `request()`).

### Security Considerations
- Test fixtures must NEVER use production-shaped secrets.
- Cleanup must run even on test failure — wrap in `afterEach` with try/catch.

### Performance Considerations
- Per-file schema isolation is slow; per-test transaction rollback is fast. Default to transaction-based isolation.
- A full unit test run must complete in under 60 seconds on a warm machine.

### Edge Cases
- Tests that span multiple transactions (e.g. testing transactional outbox) cannot use rollback isolation — provide an opt-out helper.
- Parallel test runners and shared DB: either serialize integration tests or use per-worker schemas.

## Delivery

- [ ] `pnpm test` runs unit tests across web and api with at least one example test in each.
- [ ] `pnpm test:integration` boots Prisma migrations against the test DB and runs at least one integration test (E2E hit to `/healthz` and a DB write).
- [ ] `createTestContext()` rejects any fixture call without `organizationId` (or auto-creates one and returns it).
- [ ] An integration test demonstrates tenant isolation: an entity created under org A is NOT visible when querying under org B.
- [ ] Test conventions documented in `packages/testing/README.md`.

### Testing Requirements
- The test harness itself has a self-test: `createTestContext()` must clean up between calls.
- CI from PF-009 runs both `pnpm test` and `pnpm test:integration` jobs.
