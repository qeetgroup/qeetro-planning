## Content

### Description
Add the Prisma migration foundation under `packages/database`: Prisma schema with shared audit conventions, generated client, migrations folder, seed script, and ID/audit column conventions used by every future tenant-scoped table.

### Business Context
The database schema is the single biggest architectural lock-in point in the entire system (see [§15 of the issue catalog](../../docs/planning/04-issue-catalog.md)). Every domain — identity, organizations, issues, comments, AI runs, audit logs — depends on the conventions baked in here. We must establish them once, before any real schema is written in Sprint 2.

### Problem Statement
There is no schema, no Prisma client, no migration tooling. Sprint 2 cannot start until ID conventions (cuid vs uuid), audit columns (`created_at`, `updated_at`, `deleted_at`), tenant scoping (`organization_id`), and migration workflow are settled.

### Scope
- `packages/database`:
  - `prisma/schema.prisma` with `datasource`, `generator`, and one placeholder `Health` model (so migrations can be exercised).
  - `prisma/migrations/` folder (Prisma manages this).
  - `prisma/seed.ts` that creates a single seed row in `Health`.
  - `src/index.ts` re-exporting `PrismaClient` as a singleton-safe instance for use by `apps/api` and `apps/worker`.
  - `src/conventions.md` (or appendix in README) documenting:
    - ID strategy: `cuid()` for primary keys (string).
    - Every tenant-scoped table includes `organizationId String` and a foreign key to `organizations(id)`.
    - Audit columns: `createdAt DateTime @default(now())`, `updatedAt DateTime @updatedAt`, `deletedAt DateTime?` (only when soft delete is justified).
    - Snake_case in DB columns via `@map`; camelCase in Prisma.
    - Plural snake_case table names via `@@map`.
    - Composite unique indexes use `(organizationId, slug)` shape.
    - JSONB allowed only for bounded custom field values and provider payloads.
- Scripts in repo-root `package.json`:
  - `db:migrate:dev` → `pnpm --filter @qeetro/database prisma migrate dev`
  - `db:migrate:deploy` → `pnpm --filter @qeetro/database prisma migrate deploy`
  - `db:generate` → `pnpm --filter @qeetro/database prisma generate`
  - `db:seed` → `pnpm --filter @qeetro/database tsx prisma/seed.ts`
  - `db:studio` → `pnpm --filter @qeetro/database prisma studio`
- `apps/api`:
  - `DatabaseModule` providing the singleton `PrismaService` (extends `PrismaClient` with lifecycle hooks).
  - `/api/v1/readyz` updated to ping the database with `SELECT 1`.

### Technical Notes
- Prisma `>=6.x`.
- Connection pool size configured via env (`DATABASE_POOL_SIZE`, default 10).
- Use `?connection_limit=10&pool_timeout=10` in `DATABASE_URL` for production.
- Migration files committed to the repo. Never edit a committed migration; create a new one.
- The placeholder `Health` model is intentionally trivial — it exists so the workflow `migrate -> generate -> seed` can be exercised end-to-end before any real domain model is written.

### Security Considerations
- `DATABASE_URL` never logged. Lifecycle hooks in `PrismaService` must scrub URL from any error payload.
- No raw SQL in this issue.
- RLS deferred (planning doc allows enabling later).

### Performance Considerations
- Singleton client to avoid connection storms in dev with HMR.
- `previewFeatures = ["postgresqlExtensions"]` if needed later (not required for this issue).

### Edge Cases
- Migration on an empty DB must succeed from scratch.
- Migration must be idempotent (re-running `migrate deploy` is a no-op).
- HMR in dev must not create multiple `PrismaClient` instances.
