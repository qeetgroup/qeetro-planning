## Content

### Description
Add the production-grade observability baseline from day one: request IDs and correlation IDs, structured JSON logs with user/org context placeholders, health/readiness endpoints, and a metrics endpoint placeholder ready for Prometheus or an OpenTelemetry exporter later.

### Business Context
Per [§5 Observability of the architecture blueprint](../../docs/planning/02-architecture-blueprint.md), observability is required from Sprint 1, not added later. Every later feature (realtime fanout, queue processors, AI runs) depends on correlation IDs and structured logs being already in place. Retrofitting observability is far more expensive than designing for it from the start.

### Problem Statement
The API shell from PF-005 has no structured logger, no request ID propagation, no readiness check that reflects the DB and Redis status, and no metrics surface. Without these, the first incident in Sprint 2+ is unsolvable.

### Scope
- `packages/logger`:
  - Concrete `pino`-based logger with structured JSON output.
  - Methods: `trace`, `debug`, `info`, `warn`, `error`, `fatal`.
  - Built-in field redaction for: `password`, `token`, `secret`, `authorization`, `cookie`, `set-cookie`, `jwt`.
  - `child(context)` for per-request loggers.
- `apps/api`:
  - Request ID middleware: assigns or honors incoming `x-request-id` header, attaches to the request, returns it on the response.
  - Correlation ID propagated through `AsyncLocalStorage` so all logs in a request share it.
  - Logger interceptor that logs every request with: method, route, status, duration ms, request id, org id (placeholder for now — null until auth lands), user id (placeholder).
  - `/api/v1/healthz` (liveness): returns 200 if the process is up.
  - `/api/v1/readyz` (readiness): returns 200 only if DB and Redis ping succeed; otherwise 503 with a JSON list of failed dependencies.
  - `/api/v1/metrics` placeholder endpoint:
    - Returns a minimal Prometheus-format text payload with `process_uptime_seconds`, `http_request_duration_seconds`, `nodejs_version_info`. Real metric collection comes in Sprint 9 (OBS-001).
  - All routes emit one structured log line per request with sanitization rules enforced.
- `apps/worker` (if scaffolded yet — otherwise stub):
  - Logger wired identically.

### Technical Notes
- `pino` for performance and structured output.
- `pino-http` for request logging in NestJS via a custom interceptor.
- `AsyncLocalStorage` for correlation ID propagation across async boundaries.
- Do not log request bodies by default. If body logging is enabled for debugging, sanitize first.

### Security Considerations
- Redaction list MUST include `authorization`, `cookie`, `set-cookie`, `password`, `token`, `secret`, `jwt`, `apiKey`.
- No PII in logs without explicit opt-in. User IDs are fine; emails and names should not appear in default log lines.
- The `/api/v1/metrics` endpoint must be gated by network or an auth header in production (placeholder check now; full hardening in Sprint 9).

### Performance Considerations
- `pino` is fast — overhead under 1 ms per request at info level.
- Async logger writes (default).
- Do not block the event loop on log flushing on process exit; let `pino` handle it.

### Edge Cases
- A request without an `x-request-id` header gets a freshly generated UUID v4 (or cuid).
- Multiple `x-request-id` headers — use the first one.
- `/readyz` must NOT return 200 during startup before DB is ready (Kubernetes-style readiness behavior, even though we are not yet on K8s).
- Long-running requests should still emit a log line on completion, with the full duration.

## Delivery

### Acceptance Criteria
- [ ] `packages/logger` exports a `createLogger(name)` returning a structured pino logger with the redaction list applied.
- [ ] Every API request emits exactly one structured log line containing: `requestId`, `method`, `path`, `statusCode`, `durationMs`, `orgId` (null placeholder), `userId` (null placeholder).
- [ ] Sending `x-request-id: abc-123` causes the response header and all logs for that request to include `abc-123`.
- [ ] A request that includes `authorization: Bearer xxx` produces a log line where the value is redacted (e.g. `[Redacted]`).
- [ ] `/api/v1/healthz` returns 200 regardless of DB status.
- [ ] `/api/v1/readyz` returns 200 only when DB and Redis are reachable; otherwise 503 with `{ failed: ["db" | "redis"] }`.
- [ ] `/api/v1/metrics` returns 200 with a Prometheus-format text body containing at least `process_uptime_seconds`.

### Testing Requirements
- Unit tests for `packages/logger` redaction logic (table-driven: each sensitive key is redacted).
- E2E test for `/healthz` (always 200), `/readyz` (200 vs 503 under DB-down scenario), `/metrics` (returns Prometheus text).
- E2E test that confirms request ID round-trip header behavior.
